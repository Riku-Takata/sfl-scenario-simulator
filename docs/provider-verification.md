## mdfromx.com（x.md）— 性能評価用（公開指標の取得元には使わない）

不採用の理由は実装計画 §4.1。比較のため `scripts/fan/providers/mdfromx.ts` を評価専用の Provider として実装した。

### API の確認（2026-10-30、`/openapi.json` と試し呼び出し）

- `GET /api/v1/search?q=&feed=latest&limit=&since=&cursor=&format=json&full=true&require_live=true`。キー不要。
- `require_live=true` で Web 検索の断片への劣化を 503 にできる。取得元は `X-Source` ヘッダーと `source`（今回はすべて `xsearch` = アカウントのセッションによる検索）。
- 投稿のフィールド: `id`（数字）、`created_timestamp`、`author.id`（数字）、`likes`・`retweets`・`replies`・`views`・`bookmarks`。**`quotes` と `lang` は返らなかった**（試した 16件すべて）。結果は新しい順。
- 検索は 7日より前まで遡れる（期間を指定しないと約44日前の投稿まで返った）。`since` で 7日に絞れる。
- `limit=100` を指定しても、1ページは 20件前後。
- 期間内を取り切っても `nextCursor` が返り、次のページは `warnings: ["empty_page"]`・0件になる。Provider ではこれを打ち切りとして扱い、件数を数える。
- 枠: 検索 1分5回・アカウント枠 15分10回（IP単位、キャッシュに当たった分は数えない）。1回の実行（3チーム × 3ページ）でほぼ使い切る。

### 評価結果（2026-10-30 05:17 UTC、直近7日、3チーム × 最大3ページ）

`npx tsx scripts/fan/eval/provider-eval.ts --providers mdfromx --pages 3`。本番と同じ収集処理を、メモリ上の DB と本文を読まない分類器で動かした。

| 1呼び出しあたりの件数 | 9.0件 |

| チーム | 取得件数 | ユニーク投稿者 | 取り切れたか | 最新 / 最古（時間前） | like・repost・reply がそろう | quote までそろう |

読み取れること:
1. **cr・zeta は 7日で 10件未満**しか取れない。このままでは関連投稿 10件未満で「データ不足」になる。原因がクエリ（チーム名 AND リーグ関連語）が狭すぎることなのか、mdfromx の検索の取りこぼしなのかは、Flovia の `count_recent` と比べないと分からない。PR 4 で検索語を作るとき、選手名・公式ハッシュタグを含めた版も試す。
2. **quote 数が返らない**ため、設計書の e（4項目がそろったときだけ使う）では熱量 T にエンゲージメントを一切使えない。
3. 1ページ 20件前後・アカウント枠 15分10回なので、ibsg のように投稿が多いチームは1回の実行で取り切れない。
4. 応答は安定して 1〜2秒。今回はエラーや劣化した結果は無かった。

Flovia との重なり（同じ投稿をどれだけ両方が取れているか）は、`FLOVIA_KEY` を設定して Flovia Provider を入れたあとに同じスクリプトで測る。
