### 公開サーバーカード（2026-10-30 取得、`https://api.flovia.dev/.well-known/mcp/server-card.json`）

- X 系ツールは `flovia_x` の1つ。`action` で `search_recent` / `count_recent` / `post` / `quote_posts` / `user_by_username` / `user_posts` を切り替える。
- 必須引数は `request_text`（1〜8192字）と `purpose`（1〜500字）。どちらも Flovia が保持・共有し得るので、固定の汎用文にする。
- `max_results`: search_recent は 10〜100。ページ送りは `cursor`（前回の `next_cursor`）。差分は `since_id`。期間は `start_time` / `end_time`（UTC、直近7日以内）。`sort_order` は `recency` / `relevancy`。
- `operation_id` を引数で渡せる。
- 使用率は `flovia_status`（five_hour / week の `used_pct`, `resets_at`）。

|---|---|---|---|

合計 36件で 5時間窓 48%・週次窓 18%。**1件あたり 5時間窓 約1.3%・週次窓 約0.5%** で、無料枠は 5時間あたり約75件、週あたり約200件に相当する（四捨五入された使用率からの概算）。購入残高は $0.00 で、ここまでの請求は無し。

実装計画の前提への影響:
- `max_results: 100` の1ページだけで 5時間窓を使い切る。`runCollection` の既定値 100 のまま定期実行してはいけない。
- 使用率の確認はページの前後でしかできないので、停止ライン（5時間窓 70%・週次窓 60%）を1ページで飛び越え得る。
- `estimateCostPerCall` は呼び出し回数あたりの消費を見積もるが、実際の消費は返却件数に比例する。
- 週次窓 60% までに使えるのは週 約120件。3チームの7日分は取り切れる見込みだが、ibsg の総数は未確認で、チームを増やす余地はほとんど無い。

## 2 Provider の比較（2026-10-30 05:37 UTC、3チーム × 1ページ）

`npx tsx scripts/fan/eval/provider-eval.ts --providers mdfromx,flovia --pages 1 --max-results 20`。本番と同じ収集処理を、メモリ上の DB と本文を読まない分類器で動かした。

| 指標 | mdfromx | Flovia |
|---|---|---|
| 呼び出し・エラー | 3回・0 | 3回・0 |
| 応答時間の中央値 / 最大 | 1.34秒 / 1.94秒 | 0.95秒 / 1.05秒 |
| 4項目のエンゲージメントがそろう割合 | 0% | 100% |

| チーム | mdfromx 保存件数 | Flovia 返却 / 保存件数 | 両方で取得 | mdfromx のみ | Flovia のみ | Jaccard |
|---|---|---|---|---|---|---|
| cr | 6 | 5 / 5 | 5 | 1 | 0 | 0.83 |
| zeta | 9 | 6 / 4 | 4 | 5 | 0 | 0.44 |
| ibsg | 19（続きあり） | 20 / 19（続きあり） | 15 | 4 | 4 | 0.65 |

読み取れること:
1. **cr・zeta の少なさは、主にクエリの狭さが原因とみられる。** Flovia も 7日で 5〜6件しか返さず、取り切っている。mdfromx より少ない分は、Flovia の説明どおり「すべての投稿を返すわけではない」ためと考えられる。
2. **zeta・ibsg の返却と保存の差は取得の問題ではない可能性が高い。** 収集処理は既知の投稿IDを読み飛ばすので、複数チームに一致する投稿は、評価用の分類器では先に処理したチームにしか入らない。原因の確認はしていない。この差があるので、上の重なりは参考値にとどめる。
3. ibsg は 1ページで打ち切っているので、重なりが低いのは比較範囲の差も含む。
4. PR 4 で検索語を作るとき、選手名・公式ハッシュタグを含めた版を試す。ただし件数が増えるほど無料枠の消費も増えるので、`count_recent` の消費を確かめてから決める。

## mdfromx.com（x.md）— 性能評価用（公開指標の取得元には使わない）

不採用の理由は実装計画 §4.1。比較のため `scripts/fan/providers/mdfromx.ts` を評価専用の Provider として実装した。

### API の確認（2026-10-30、`/openapi.json` と試し呼び出し）

- `GET /api/v1/search?q=&feed=latest&limit=&since=&cursor=&format=json&full=true&require_live=true`。キー不要。
- `require_live=true` で Web 検索の断片への劣化を 503 にできる。取得元は `X-Source` ヘッダーと `source`（今回はすべて `xsearch` = アカウントのセッションによる検索）。
- 投稿のフィールド: `id`（数字）、`created_timestamp`、`author.id`（数字）、`likes`・`retweets`・`replies`・`views`・`bookmarks`。**`quotes` と `lang` は返らなかった**（試した 16件すべて）。結果は新しい順。
- 検索は 7日より前まで遡れる（期間を指定しないと約44日前の投稿まで返った）。`since` で 7日に絞れる。
- `limit=100` を指定しても、1ページは 20件前後。
- 期間内を取り切っても `nextCursor` が返り、次のページは `warnings: ["empty_page"]`・0件になる。Provider ではこれを打ち切りとして扱い、件数を数える。
- 枠: 検索 1分5回・アカウント枠 15分10回（IP単位、キャッシュに当たった分は数えない）。1回の実行（3チーム × 3ページ）でほぼ使い切る。

### 評価結果（2026-10-30 05:17 UTC、直近7日、3チーム × 最大3ページ）

`npx tsx scripts/fan/eval/provider-eval.ts --providers mdfromx --pages 3`。本番と同じ収集処理を、メモリ上の DB と本文を読まない分類器で動かした。

読み取れること:
1. **cr・zeta は 7日で 10件未満**しか取れない。このままでは関連投稿 10件未満で「データ不足」になる。原因がクエリ（チーム名 AND リーグ関連語）が狭すぎることなのか、mdfromx の検索の取りこぼしなのかは、Flovia の `count_recent` と比べないと分からない。PR 4 で検索語を作るとき、選手名・公式ハッシュタグを含めた版も試す。
2. **quote 数が返らない**ため、設計書の e（4項目がそろったときだけ使う）では熱量 T にエンゲージメントを一切使えない。
3. 1ページ 20件前後・アカウント枠 15分10回なので、ibsg のように投稿が多いチームは1回の実行で取り切れない。
4. 応答は安定して 1〜2秒。今回はエラーや劣化した結果は無かった。
