## 1. 目的と実施順序

毎節、両Divisionに対して「何が起きたか」「なぜ勝敗が分かれたか」「どう流れが変わったか」が分かる解説を自動で公開する。公式結果は先に届け、詳細記事が未完成であることを明示する。Vercelと自宅サーバーは同じ公開成果物を配信する。

| 段階 | 実施内容 | 完了の条件 |
|---|---|---|
| P0：当面の品質確保 | F第4節の編集原稿を追加 | 3チーム戦・10個人対戦に、映像・実況で確認した解説がある |
| P1：配信同期と表示 | 配信経路を調査・修正し、同じ成果物を両環境へ配布。「作成中」等を表示 | 世代と内容の差を検出でき、自宅が自動追従する。未完成を完成と表示しない |
| P2：生成工程 | 区間解決、根拠抽出、検証、執筆、品質判定、再解析を分離 | Sの詳細原稿を構成の基準にした比較検証に合格する |
| P3：毎節の自動運用 | GitHub Actionsで結果検知から公開・再開まで実行 | 次節で手動起動なしに速報→詳細へ進み、異常時も状態を正しく示す |

初版の設計作成後、P0の編集原稿とローカルでの配信・生成工程の変更を実装した。本番への反映と自宅タスクの登録は別途、PRマージと運用設定の確認を経て行う。

## 3. 採用する基本方針

1. 公式結果の速報公開と、時間を要する詳細生成を別の処理にする。
2. 正本はGitHubに確定したコード・公開用データ。Astroの静的構成を維持する。
3. 公開ビルドはCIで一度だけ作成し、同一の静的ファイルを両配信先へ渡す。
4. 編集原稿は引き続き最優先。自動生成で上書きしない。
5. 自動記事は、根拠が検証でき、内容の品質基準を満たしたものだけを詳細版として公開する。
6. 試合・個人対戦単位で進捗を保存し、途中停止しても続きから再開する。
7. 「完成まで時間がかかる」と「確認できず停止している」を画面でも運用でも区別する。
8. S/Fの固定順による予算の偏りをなくす。新節になっても前節の未完了作業を消さない。

常時完全同時の切替は、独立した2配信先と自宅回線では保証できない。同一成果物の使用により内容の分岐を防ぎ、反映待ちの時間差は自動検知・再試行で解消する。

## 4. 全体の処理フロー

```text
公式日程・結果の定期確認
  ├─ 新しい結果 → 公式ログ保存 → 速報と「作成中」を公開用データへ反映
  └─ 未完了作業 → 永続キューから再開
                        ↓
動画特定 → 区間確認 → 時刻付きの出来事・実況要旨の抽出
                        ↓
公式ログとの照合 → 同じ出来事の対象区間を再確認
                        ↓
検証済み根拠で執筆 → 事実・文章・充足度の検査
  ├─ 合格 → 試合単位で詳細版へ更新
  ├─ 不足 → 追加調査の作業を保存して次回へ
  └─ 上限・要確認 → 明示的な保留状態で保存
                        ↓
公開用データ確定 → テスト → CIで共通ビルド
                        ↓
Vercelへ配信・照合 → リリース確定 → 自宅サーバーが同じ成果物へ追従
```

画像タグ・決着チップ等の補助情報は、本文に必要な根拠の収集より後に処理する。補助情報の未完了だけで、合格した解説の公開を止めない。

## 5. P0：F第4節の編集原稿

### 5.1 対象と書式

既存 `src/data/editorial-recaps.json` に、`div-f-sec4-m1`〜`m3` の見出し・総評、実在する10個人対戦の `summary / keyPoints / writtenAt` を追加する。S第4節と同じ画面構造で表示する。

目安は、各対戦の要約1〜2文、見どころ2〜3段落、各段落に具体的な出来事とその意味を含める。試合総評は先鋒→中堅→大将→延長のつながりを示す。文字数や段落数を満たすために、未確認の攻防を加えない。

### 5.2 作成・検証の手順

1. 公式ログから全10対戦の選手、ゲーム・ラウンド推移、ゲームごとの使用キャラ、獲得点を一覧にする。キャラ変更は単一の代表キャラだけで扱わない。

3. 各対戦の映像・実況を確認して原稿を書く。旧キャッシュは調査の候補に使うが、食い違う観測を確定事実として転記しない。
4. `editorial-evidence.json` に文章・要点のID、動画ID、開始/終了秒、公式根拠への参照、確認者・確認時刻を保存する。P0では既存原稿スキーマを壊さない補助ファイルとする。
5. 得点・逆転・フルセット等を自動照合し、技名・因果関係・実況の意味を映像で確認する。実況の評価と記事側の断定を区別する。

### 5.3 完了条件

3試合・10対戦すべてが `editorial` になり、勝敗とラウンド推移に矛盾がない。具体的な攻防・転機・勝敗への意味を説明し、各重要記述を根拠へたどれる。既存S原稿は変えない。映像等を確認できない対戦は未完成とし、F全体を完成扱いにしない。

## 6. P1：同一成果物による配信同期

### 6.1 ビルドの正本

CIが確定コミットをcheckoutし、固定したNode・lockfileで `npm ci`、検証、`astro build` を実行する。`SITE_URL` は本番の正規URLを明示し、配信先の環境変数によるHTMLの差をなくす。書き換え途中のJSONからビルドしない。

共通パッケージは次の内容とする。

```text
sfl-site-<buildId>.zip
  dist/                   # Astroが生成したHTML、JS、CSS、公開JSON
  runtime/serve-static.mjs # この成果物に対応する配信コード
  runtime/Dockerfile      # 生成済みdistをCOPYするだけ。Astroを再ビルドしない
  vercel/config.json      # Build Output API用ルーティング・ヘッダー
  release-manifest.json   # ファイル一覧とSHA-256、元コミット等
```

`buildId = sourceCommit + workflowRunId + runAttempt` を基本とする。`sourceCommit` は生成データをコミットした後のSHAであり、単に起動イベントのSHAを使わない。別途 `resultsHash / recapHash / pipelineVersion` とファイルごとのハッシュを持つ。

`/build-info.json` を両環境で同じ内容として公開し、サービス名、buildId、sourceCommit、ビルド時刻、結果/解説の更新時刻、最新節を返す。マニフェスト自身等を除いたファイル一覧から内容ハッシュを作り、自己参照を避ける。配信先の適用時刻・失敗履歴はサーバー側の別記録に置く。

### 6.2 Vercelとリリースの確定

1. CI内の成果物をActions artifactとして保存し、同じファイルから `.vercel/output/static` とルーティング設定を作る。
2. Build Output API形式で `vercel deploy --prebuilt` を使う。VercelでAstroをもう一度実行しない。
3. `/recap`、`/build-info.json`、代表的なJS/CSSの取得とハッシュを検証する。ディレクトリ型URL、404、`/api/health` から生成済みhealth JSONへの対応、CSP、キャッシュ指定も変換時の検査対象とする。
4. 既存Vercel Git連携の本番URLが同じ `buildId` と `contentHash` を返し、配信対象の `dist` 全ファイルのSHA-256がCI成果物と一致した後に、共通zip・マニフェストを `sfl-site-*` タグのGitHub Releaseへ保存する。差分・未反映・15分以内に反映されない状態ではReleaseを作らず、自宅同期を開始させない。
5. リリース一覧では `sfl-site-*`、非draft、非prereleaseを明示して選び、他用途のReleaseを取得しない。公開順は専用の直列公開処理で管理する。

移行時にVercelのGit pushによる本番自動ビルドを停止し、本番公開の入口をCIに一本化する。プレビューは残せる。CLI導入前に既存の本番URL、プロジェクトID、分析スクリプト、ヘッダーの挙動を確認する。

本番公開処理は共通concurrencyで直列化し、配信直前に対象データの世代を安定版と比較する。古いsnapshotのビルドが遅れて終わっても新しい安定版を上書きしない。Vercelへの配信とRelease確定は2段階の処理として記録し、途中停止時は配信済みbuildIdを照合してRelease確定だけを再開できるようにする。

Actions artifactはジョブ間受け渡し用で、保持期限のあるキャッシュを自宅の永続的な配布元にしない。安定Releaseの現行版と直前2版を保持し、ロールバック可能にする。

### 6.3 自宅サーバーの自動追従

新設 `scripts/sync-sfl-release.ps1` をWindowsタスクスケジューラで5分間隔・起動時に実行する。GitHubからの外向き取得で完結させ、自宅への受信接続や自宅上での汎用Actions runnerは前提にしない。

1. 安定ReleaseのbuildIdとローカルの適用済みIDを比較する。同じならHTTPの世代確認だけで終了。
2. 異なる場合は `data/app-data/sfl-deploy/releases/<buildId>` にダウンロードし、zip内パス、ファイル一覧、SHA-256を検証する。
3. 同梱runtimeからローカルのイメージ `homeserver-sfl-release:<buildId>` を作る。依存の再解決・Astroの再ビルドはしない。Composeはこのイメージを指定して更新する。
4. コンテナ内、ホストの公開ポート、実際の利用URLで、`service=sfl-scenario-simulator`、buildId、内容ハッシュ、レポート表示を確認する。HTTP 200だけで成功扱いにしない。
5. 合格後に適用記録を保存する。失敗時は前のイメージへ戻して再試行状態を残す。検証に使ったURL・失敗地点をログに記録する。

タスクの多重起動はOSの排他で防ぐ。タスクの実行アカウントと通常運用のDocker contextを固定する。展開・削除先は上記の専用配下に限定し、現在/直前の配信物を削除対象にしない。

既存 `update-sfl-simulator.ps1` の本番用途は「安定Releaseへ同期」に置き換える。開発ビルドは明示的な別モードに分ける。`trigger-sfl-pipeline.ps1` は起動に加え、対象run、重複抑止、定期的な結果確認を記録する。

### 6.4 同期の目標・監視

Vercelでリリース確定後、自宅がオンラインなら通常10分以内に同じbuildIdへ追従する目標とする。15分超の差は同期異常としてローカル監視・運用サマリーに出す。回線断・端末停止中は直前の正常版を配信し、復旧時に自動追従する。

古いリリースを遅れて適用しないよう、適用直前に安定版を再確認する。通常処理で世代を巻き戻さず、ロールバックは明示的な運用操作として区別する。

## 7. P2：詳細解説の生成工程

### 7.1 動画と区間の特定

公式結果で各チーム戦の終了を確認し、公式チャンネルから対象節の動画を検出する。候補はシーズン・Division・節・チーム/選手で照合し、曖昧なものは自動採用しない。

区間は「確認済みの手動補正→チャプターと試合順の整合性→オーダー発表等からの候補抽出→映像/音声による実選手と開始の照合」の順で決める。番号だけでなく前後の時間順を検証する。

チャプターに欠落・矛盾があれば、取得後15分・1時間・6時間・翌日の間隔を目安に再取得する。既に1件あることを理由に永久キャッシュしない。補正にはvideoId、区間、理由、確認者、確認日時を付ける。

### 7.2 根拠の抽出

まず実況・解説音声と映像から、次の形で候補を作る。字幕がなくても音声を扱える経路を用意し、字幕の存在を必須条件にしない。

```ts
type RecapEvidence = {
  id: string;
  sectionId: string;
  matchId: string;
  boutId?: string;
  kind: 'official' | 'visual' | 'commentary' | 'derived';
  videoId?: string;
  startSec?: number;
  endSec?: number;
  gameIndex?: number;
  roundIndex?: number;
  playerIds: string[];
  observation: string; // 具体的な観測または実況の要旨
  officialRefs: string[];
  status: 'candidate' | 'verified' | 'rejected' | 'disputed';
  extractorVersion: string;
  verifierVersion?: string;
};
```

実況の評価は「解説が○○を勝因として挙げた」という発言の記録として扱い、機械が断定した原因と区別する。全文の文字起こしや長い引用は公開データに含めず、必要な観測・短い要旨と時刻を保存する。

公式ログから、ゲームごとのキャラ、先取・逆転・フルセット、得点経過を確定する。連勝・今季初勝利・順位への影響は、その節以前の公式結果から計算し、根拠の時点を固定する。未取得の過去情報から初勝利等を断定しない。

### 7.3 検証

最初に抽出した候補の同じ短い区間を再確認する。別の自由要約を作って共通部分を探す方式は廃止する。勝敗の一致だけで出来事全体を合格させない。

検証は、公式の勝者・ラウンド順・キャラ・得点との機械的照合と、映像/音声による出来事の確認を組み合わせる。モデルの `supportedBy` 自己申告だけではverifiedにしない。技名などの不一致があれば区間を再確認し、解消しない細部は削除する。同じモデルを2回呼んだだけで独立した裏付けができたとは扱わない。

通常の抽出は標準fpsで行い、短い攻防の再確認に限ってfps/解像度を上げる。モデル名・プロンプト・入力動画・区間・検証バージョンを記録する。特定のモデルが使えないときに、未評価の軽量モデルへ自動的に品質基準を下げない。

### 7.4 執筆

執筆に渡す材料はverified根拠、公式ログ、検証済みの背景情報のみ。各文・要点は `evidenceIds` を持ち、存在しないIDや対象試合と無関係なIDを拒否する。

記事の構成は、対戦の結果、序盤の狙い、相手の対応、流れが変わった場面、決着、チーム戦としての意味を基本とする。実際に転機がなければ、主導権を維持した具体的な理由を書く。根拠のない心理や、観測できていない対策の準備過程を創作しない。

Boutは要約1〜2文と、具体的な見どころ2〜3段落を目安にする。試合総評は150文字に制限せず、概ね180〜350字を目安とする。情報が少ない試合は無理に長くせず、品質不足として扱う。検証後の本文を画面へ渡し、定型の勝敗文へ常に戻す現仕様を変更する。

動画由来の要点を採用しても、公式ログから分かる逆転・連取等の有用な説明を失わないよう統合・重複除去する。編集原稿と自動原稿は別々に保存し、表示の優先順位は「適用可能な編集原稿→品質合格した自動原稿→公式ログの速報」とする。

### 7.5 品質判定

| 判定 | 合格条件 | 不合格時 |
|---|---|---|
| 公式整合性 | 勝者、得点、ゲーム/ラウンド順、使用キャラに矛盾がない | 自動公開を止め、公式情報から再構成 |
| 根拠 | 重要な具体記述・評価の帰属が検証済みIDに結び付く | 記述削除または該当区間の再確認 |
| 内容 | 勝敗の意味と、勝負を分けた具体的な攻防を説明する | 不足する観点を対象指定して再抽出 |
| 展開 | 対応の変化/転機、または支配が続いた理由が分かる | 同上。転機を無理に要求しない |
| チーム戦 | 得点経過と大将・延長の役割を正しく説明する | 公式ログから修正 |
| 文章 | 定型句の羅列・他対戦の流用・中身のない誇張がない | 再執筆 |

重要な公式矛盾は0件、重要記述の根拠参照率は100%を必須とする。LLMの自己採点のみで合格にしない。S/Fの同じ試合について旧処理と新処理を比較し、原映像を確認した編集評価で「具体性・展開・因果の根拠・読みやすさ」を確認する。Sの既存原稿そのものを事実の正解として固定しない。

原則は個人対戦の合格→試合総評の合格をもって試合単位で詳細版を公開する。個別対戦は先に詳細を公開できるが、試合全体は `partial` とする。1対戦の欠落を、全試合完成という表示で隠さない。

## 8. 状態管理と画面表示

### 8.1 データの分離

既存の `videoStatus` と `narrationStatus` の3値を完了判定の正本にしない。v2では次を分離する。

```ts
type ArticleState = {
  workflow: 'queued' | 'waiting_video' | 'waiting_window' |
    'extracting' | 'verifying' | 'writing' | 'reviewing' |
    'retry_wait' | 'paused' | 'needs_review' | 'completed';
  quality: 'not_evaluated' | 'insufficient' | 'passed' | 'invalid';
  publication: 'results_only' | 'partial' | 'detailed';
  publishedRevision?: string;
  candidateRevision?: string;
  updatedAt: string;
  nextAttemptAt?: string;
  reasonCode?: string;
  lastErrorCode?: string;
};
```

`publishedRevision` と作成中の `candidateRevision` を分け、品質合格した既存記事を再生成の失敗で消さない。公式訂正により既存記事が矛盾した場合は該当原稿を無効化し、訂正済み速報と「解説を確認中」を表示する。

### 8.2 表示仕様

| 状態 | ユーザー向け表示 |
|---|---|
| 結果取得済み・未完成 | **現在、詳細な解説記事を作成中です。試合結果・ラウンド推移は公式記録を反映しています。** |
| 動画待ち | 公式配信アーカイブの公開を待って、詳細な解説記事を作成します。 |
| 一部だけ完成 | 詳細な解説は一部公開済みです。残りの対戦は現在作成中です。 |
| 自動再試行予定 | 詳細な解説記事の作成に時間がかかっています。確認が終わり次第、更新します。 |
| 停止・人の確認が必要 | 詳細な解説は現在確認中です。公式の試合結果と配信アーカイブをご覧いただけます。 |
| 合格し公開済み | 詳細解説を公開しました。更新日時を表示 |
| 既存記事を表示しつつ再生成 | 公開済み記事を維持し、必要な場合だけ「解説を更新中」と表示 |

節上部、閉じた試合カード、展開後の総評、未完成の個人対戦に表示する。節の完成数は「3試合中1試合の詳細を公開済み」のように数え、API呼び出し回数や不正確な進捗パーセントは見せない。技術的な失敗理由は運用ログに置く。

初期表示の静的HTMLにも対象節の未完成状態を出し、React起動前でも認識できるようにする。文字とアイコンを併用し、色だけで区別しない。

更新処理そのものが停止した場合に備え、未完成状態には `lastProgressAt / delayAfter / reviewAfter` も公開する。ブラウザー側でも時刻経過から遅延表示へ切り替え、古い「順調に作成中」という表示を無期限に続けない。これは生成の完了や失敗を推測するものではなく、更新が確認できていないことの表示とする。

### 8.3 開いたままのページ

公開用の `/data/recap-status.json` は軽量な状態、原稿リビジョン、更新時刻だけを持つ。表示中のタブは2分間隔と再表示時に確認し、差分があれば「詳細解説が更新されました。最新の内容を表示」を出す。ユーザー操作で最新の静的ページへ移動し、開閉状態と選択Divisionを可能な限り復元する。本文だけを無条件に差し替えてスクロール位置を崩さない。

自宅配信とVercelの両方で、状態JSONとbuild-infoに `Cache-Control: no-store`、ハッシュ付きJS/CSSに長期キャッシュを指定する。必要な同一オリジン取得をCSPで許可する。

## 9. P3：GitHub Actionsの自動運用

### 9.1 ワークフロー構成

| 処理 | 役割 | 起動 |
|---|---|---|
| `auto-update.yml`（再編） | 軽い公式結果確認、キュー整合、速報確定、必要な後続処理の呼び出し | schedule / workflow_dispatch |
| `recap-worker.yml`（新設・再利用可） | 時間/費用上限内でキューの作業を進め、途中結果を確定 | workflow_call / 明示dispatch |
| `publish-site.yml`（新設・再利用可） | 確定SHAを検証・ビルド・Vercel配信・安定Release化 | workflow_call / mainへのコード・公開データ更新 / 再試行 |
| 自宅の同期タスク | 安定Releaseを取得・適用・実配信を照合 | 5分ごと / OS起動時 |

速報確定後は先に公開を呼び、動画解析の完了を待たせない。workerは進んだ試合や状態を区切りよく保存し、その都度または最大5分のまとめ単位で再公開する。何も変化していない定期確認ではコミット・ビルドしない。

GITHUB_TOKENによるpushで次のpushワークフローが必ず動くと仮定せず、必要な後続処理は同じrun内の `workflow_call` または明示dispatchで接続する。Buckler集計や人のコード更新も公開トリガーに含める。

軽量確認はキューの期限・日程を先に読み、処理不要なら依存のインストールやLLM呼び出しへ進まない。状態ファイルだけの変更を含め、速報と公開中状態に差がある場合は公開処理を呼び、生成ワークフロー自身の更新で無限に再起動する構成を避ける。

### 9.2 終了検知と再開

公式日程から対象日を判断する。初期設定は毎時7・22・37・52分の軽量確認とし、放送予定の前後、結果未確定、未完了キューがあるときだけ必要な外部取得を行う。固定の曜日だけに依存しない。公式APIが終了結果を返した時点を検知の起点とし、実際のKO時刻と同一とは扱わない。

GitHub scheduleは遅延し得るため、自宅の既存トリガーを補助経路に使う。実行中runの有無と最終確認時刻で過剰なdispatchを抑制する。自宅停止中でもGitHub scheduleで進められる構成にする。

目標値は次のとおり。実測で調整し、サイトに完成時刻を断言しない。

| 指標 | 初期目標 |
|---|---|
| 結果検知から速報・作成中表示の公開 | 10分以内 |
| 利用可能な動画・区間の確定後から詳細公開 | 通常2時間以内を目指す |
| 長時間未完了の扱い | 6時間で遅延表示、24時間で確認待ちへ移行し運用サマリーに残す |
| 自宅配信の追従 | 安定Release確定後、通常10分以内 |

### 9.3 永続キューと競合

`recap-jobs.json` をGit管理の永続キューとし、`season/section/match/bout/stage/inputHash/pipelineVersion` を作業の識別に使う。`attempts / nextAttemptAt / deadline / failureReason / completedEvidenceIds` を保存する。Actions cacheのみへ保存しない。

処理状態の変更は短い直列のcommit処理へ集約する。重い抽出はリポジトリ外の一時成果物へ出し、反映直前に最新HEADとinputHashを確認する。公式結果や編集原稿が変わっていたら古い成果を反映しない。push競合では最新状態で再判定し、解説JSONの衝突を盲目的にrebaseして通さない。

同じキーの作業は二重に確定しない。中断後の残存作業は期限付きのleaseを失効させて再開する。runner強制停止では最後のAPI呼び出しが再実行される可能性があるため、API呼び出しの完全な一度限り実行は保証しない。

Actionsのconcurrencyは排他用であり、作業そのものの保管場所にしない。起動runが間引かれても、次回キューを読み直して未完了を回収する。start.ggだけが更新された場合でも解説キューの確認を省略しない。

### 9.4 上限・失敗・再試行

workerは新規処理開始を20分で止め、各APIにもタイムアウトを設ける。上限接近時は新規呼び出しを止めて保存し、タイムアウト前に終了する。S/Fを交互に扱い、最終処理時刻が古い作業を優先する。公開済みの古い試合を際限なく再生成しない。

| 原因 | 対応 |
|---|---|
| 動画未公開・チャプター不足 | 待機し、取得間隔を徐々に広げる |
| 一時的429/503/ネットワーク | Retry-Afterとエラー内容を確認し、バックオフ＋揺らぎで再試行 |
| 日次枠の枯渇 | リセット以降へ予約。別モデルへ無制限に切り替えない |
| 事実の不一致・情報不足 | 対象の出来事/区間を指定して再検証。1段階3回を初期上限とする |
| 認証・設定エラー | 自動連打せずpausedへ。次の正常な設定確認または運用操作で再開 |
| 品質上限到達 | needs_reviewへ。確認待ち表示を続け、勝手に完成にしない |
| 公開失敗 | 完成原稿は保持し、ビルド/配信だけ再試行する |

`MAX_CALLS / MAX_VIDEO_SECONDS / MAX_ESTIMATED_COST / MAX_ATTEMPTS` を全体・節単位で設定し、入力・出力トークン等の実績を記録する。単なる「API枠内」でなく、高品質モデルに必要な枠を評価時に測る。費用上限とモデル許可リストが未設定なら新しい有料枠を自動使用せず、既存許可範囲または保留状態で動作する。費用を下げる際は重要区間の再検証を優先し、根拠の基準は下げない。

## 11. 互換性と移行

1. P0は既存の編集原稿形式で追加し、表示を先に改善する。
2. `schemaVersion: 2` を導入し、旧データは読み込み時に変換する。編集原稿は対象公式結果との適合性を確認して詳細版へ移行する。
3. 旧 `complete` は「高品質」を意味しないため、自動原稿を無条件にpassedへ昇格しない。旧記事を参考表示する場合は速報/部分版として区別する。
4. 旧 `video-facts.json` は参照用に維持し、検証済み根拠へ変換できたものだけをv2で使用する。新しい抽出・検証・執筆の各バージョンをキャッシュキーへ含める。
5. `--force` と、対象限定の `--reanalyze --section / --bout / --stage` を分ける。全節のキャッシュを毎回消す運用にしない。
6. workerは新旧工程を切り替えられるフラグを持つ。新工程の不具合では直前の公開記事と共通成果物へ戻せるようにする。
