作成日：2026-10-21（JST）
状態：再設計を実装済み。実映像の小規模疎通を確認したが、ゴールドセット評価は未完了。
対象：`docs/recap-quality-and-delivery-design.md` の動画理解、記事執筆、品質判定、受入評価。

## 1. 結論

Geminiに動画・音声の要約や解説文を作る能力はある。しかし、現在の保存データと品質ゲートからは、Division S相当の内容を安定して作れる証拠がない。実測上、映像から抽出済みの話題に時刻情報がなく、新工程の映像根拠として再利用できない。さらに、現行品質判定は根拠IDが付いた無関係な文章を合格にする。

したがって「複数モデル一致→別モデルがverified→文字数等の検査に合格すれば自動公開」という現行案を品質保証の根拠にしない。先に対戦単位の評価セットを作り、動画理解方式・根拠抽出・文章生成を同じ映像で比較し、人手評価と重大誤り率で採用方式を決める。評価が終わるまでは自動記事をshadow運用し、公開済み原稿と公式速報を維持する。

対象はリポジトリの `src/data/video-facts.json`、`src/data/editorial-recaps.json`、`src/data/match-recaps.json`。外部APIは呼ばず、保存データを読み取り集計した。

| 勝者ゲートに合格したモデル実行 | 35 | 話題の内容までは検証していない |
| 合格実行に含まれる話題 | 90 | 旧プロンプトから抽出された話題 |
| 開始・終了時刻が両方ある話題 | **0** | 新しい区間再検証へ接続できない |

現行コードは、動画解析済み (`status=complete`) のキャッシュを再解析しない。一方、新しい根拠台帳は時刻付き候補だけを対象区間検証へ送る。そのため旧キャッシュを残したまま新工程を起動すると、90件の話題は動画根拠へ昇格せず、リッチな記事の入力にならない可能性が高い。抽出器/プロンプトのバージョンをキャッシュキーに含め、旧結果を明示的にstaleとして再解析対象にする必要がある。

### 2.2 品質ゲートの反例

`evaluateBoutArticle` に、実際の対戦・公式ラウンドと無関係な会場天候や雰囲気の文章を与え、別の映像事実IDを各文に添えた。要約60字以上、要点2件、映像根拠2件など現行条件を満たす入力は `passed` になった。ゲートは参照IDの存在と形式を確認するが、文章が参照根拠から導けるかを比較していない。

これはテスト実行時の合成データによる再現であり、実際に公開済み記事がこの反例を含むという意味ではない。ただし、現行の `passed` を編集上の品質保証として扱えないことを示す。

### 2.3 既存テストの範囲

`npm test` は **46件成功・0件失敗**。ただし、既存テスト群には新設した `evidence-ledger.ts`、`article-quality.ts`、`recap-state.ts` の検証が含まれていない。モデルの映像理解能力、根拠と文章の意味対応、編集原稿との品質比較もテストしていない。したがって、既存テスト成功は本設計の品質基準を満たす根拠にならない。

この設計書の初稿時点では `GEMINI_API_KEY` を利用できず、実映像推論は未実施だった。その後、ユーザーの指示で `.env` のキーを使った短いAPI検証を実施した。4節分の解析・A/B比較や人手採点を完了したわけではないため、採用モデルの品質は未確定のまま扱う。

### 2.4 時刻欠落につながる実装上の不整合

追加調査で、旧プロンプトは「アーカイブ全体の先頭からの秒数」を要求していたが、APIには対戦区間だけをクリップして渡していた。Geminiが実際に返した時刻はそのクリップ先頭からの相対秒だった。旧コードはアーカイブ全体の区間と比較して範囲外の話題を捨てていたため、0件の時刻付き話題が生まれる主要な原因になり得る。今回の小規模呼び出しでは、区間2632–2652秒に対し `2–10秒`、`11–20秒` や `2–10秒`、`12.5–20秒` が返ることを確認した。

15秒の対戦区間（2700–2715秒）を1 FPSで照会した際は、SA2の発動と起き上がりへの反撃という候補が返った。5 FPSの同区間は503で応答しなかった。これらの話題は人手で動画と突き合わせていないので、検出例であって正解例ではない。4/5 FPS・Agentic・音声精度を結論づけるA/B検証は未完了である。

## 3. モデルと動画入力に関する設計上の事実

動画・音声入力には現行のInteractions APIを使う。Googleの資料ではstatic動画処理は標準1 FPSで、速い動作や短い場面を落とす場合がある。staticではfpsと区間を指定できる。長尺動画や特定時点の探索向けにAgentic処理も提供されている。[動画理解の公式資料](https://ai.google.dev/gemini-api/docs/video-understanding)

運用パイプラインの既定値はstatic 1 FPSで、AgenticはAPIクライアントから試験できるが本番パイプラインにはまだ採用していない。したがって「Geminiが音声も読める」という一般仕様と、「このAPIリクエストが実況の具体的な発言を十分に拾っている」という実証は分けて扱う。

既定モデル候補はコードで確認できるが、Actions変数 `GEMINI_VIDEO_MODELS` / `GEMINI_TEXT_MODELS` が設定されていれば上書きされる。実際の呼び出しモデルは `video-facts.json` の実行記録で確認し、環境変数の値を推測しない。

## 4. 改訂する生成工程

### 4.1 対戦ごとの入力パッケージ

公式記録から各ゲームの勝者、ラウンド推移、キャラクター、チーム得点を固定し、アーカイブと対戦区間を確定する。入力ハッシュには公式結果、動画ID、区間、抽出器バージョン、モデルID、プロンプトIDを含める。旧キャッシュは削除せず、旧バージョンとして保存したうえで再解析可能にする。

### 4.2 出来事を二つの経路で集める

実況・解説の情報は音声経路で取得し、発言時刻と「実況/解説がそう評価した」という帰属を持たせる。音声認識文を機械が確認した映像事実として扱わない。

映像経路は、まずAgentic動画理解とstatic高FPSの両方を、同一の検証用対戦で比較する。static方式では全対戦を高FPSにせず、全体の出来事発見と、候補時刻の前後を切り出した詳細確認を分ける。fps値は4/5などを最初から固定せず、1/2/4/5 FPSを同じ短い局面で比較し、見落とし率と費用を見て決める。Agentic方式で発言文字起こし・動画参照のどちらが得られるかも出力で確認する。

### 4.3 根拠を原子的な観測として検証する

一つの根拠には、ひとつの観測可能な主張だけを入れる。最低限 `videoId, startSec, endSec, modality, speaker/player, observation, officialRefs, extractorVersion, verifierVersion` を持たせる。

- 公式ログ：勝敗・スコア・ゲーム順・ラウンド順の正本。映像理解モデルが上書きしない。
- 映像：画面から直接分かる行動や状況。高速区間は対象区間を拡大/高FPSで再確認する。
- 実況・解説：発話内容と話者/役割の記録。「解説はこれを勝因と評した」として扱う。
- 推論：複数根拠から導く説明。観測事実と分け、根拠の組み合わせを明記する。因果の断定は編集評価で合格した表現に限る。

別モデルの一致は候補の優先順位付けにだけ使い、真実性の証明にしない。Verifierには候補文を先に見せて同意を誘導するのではなく、対象クリップを独立に説明させた後に、編集工程で一致箇所を照合する。モデル間不一致、時刻不一致、話者不明は `uncertain` とし、記事の断定材料から外す。

### 4.4 編集記事を書く

書き手には、公式結果、検証済みの根拠カード、関連するチーム戦の得点推移だけを渡す。S/Fの編集原稿から選んだ短い見本は、語り口・段落構成の参考として明示し、試合事実の根拠としては渡さない。

対戦記事は原則として「結果と使用キャラ→試合の主導権/対応→根拠がある場合の転機→決着→チーム戦での意味」の順に構成する。材料のない段落は省略する。キーポイントの箇条書きだけで記事を代替しない。試合総評は対戦順に、先鋒・中堅・大将・延長がチーム得点へどうつながったかを説明する。

各文をひとつ以上の根拠カードへ対応付ける。心理、練習・準備、意図、戦略上の因果など映像・発言・公式データに直接現れない内容は、書き手が自然に補わないよう明確に禁止する。

### 4.5 二層の品質判定

品質状態を「事実・根拠の安全性」と「編集品質」に分ける。

**自動の公開前ゲート**は、公式勝敗・点数・ゲーム順の矛盾、存在しないID、対象外試合のID、未検証根拠、同じ要点の重複を止める。文章の各主張と根拠カードの意味対応を独立の批評工程で検査し、根拠の言い換えに見えない主張は削除または人手確認へ送る。単純な文字数を内容品質の代用にしない。

**編集品質評価**は、自動の自己採点だけで合格にしない。内容の具体性、展開の説明、因果の慎重さ、実況・映像の使い方、読みやすさ/熱量を人が採点する。最初は新旧記事を試合名・モデル名を伏せて評価し、S/F原稿を同一試合の比較対象にする。自動クリティックは人の判定と一致するかを測ってから補助に使う。

## 5. 評価セットと受入基準

### 5.1 ゴールド評価セット

S/F両方から、展開が異なる最低6対戦を選ぶ。逆転、フルセット、ストレート、キャラクター変更、実況による評価、目立った転機がない試合を含める。2名の確認者が別々に、公式情報・時刻付き映像/発話・記事として許される表現を記録する。意見が異なる記述は正解ラベルにせず、判定不能として扱う。

同一クリップを以下の条件で処理し、呼び出しモデル、プロンプト、区間、fps/処理方式、時間、トークン/費用を記録する。

1. 既存方式（static 1 FPS＋現行プロンプト）。
2. staticの候補FPS（1/2/4/5）で詳細区間を解析。
3. Agentic動画理解で同じ質問を実行。
4. 音声発話の時刻付き取得を加えた方式。

### 5.2 評価指標

| 指標 | 測り方 |
|---|---|
| 話題再現率 | ゴールドの重要出来事のうち正しく拾えた割合 |
| 事実精度 | 抽出した主張のうち根拠と時刻が合っている割合 |
| 公式整合性 | 勝敗・点数・ゲーム順の重大矛盾数 |
| 文章根拠率 | 重要な事実/因果文のうち根拠カードから支持できた割合 |
| 編集品質 | 具体性、展開、因果の慎重さ、読みやすさを各1–5で盲検採点 |
| コスト | 対戦あたりの入力/出力トークン、動画秒数、API費用、所要時間 |

採用前の仮基準は、重大な公式矛盾0件、重要主張の根拠率100%、編集項目の平均4/5以上、各Divisionで既存編集原稿の評価を下回らないこと。少数6対戦では安定性の証明にならないため、これを満たした後も次の2節はshadow運用と人手確認を続ける。編集者間の採点差が大きい場合は、基準を改訂してから合否を判定する。

### 5.3 必須の失敗注入

- 根拠IDを別対戦へ入れ替える。
- 実際の根拠とは無関係な長文をID付きで渡す。
- 技名・プレイヤー・ゲーム番号・勝敗を取り違える。
- 正しい映像観測に誤った実況解釈を紐付ける。
- 動画ID変更、古い無時刻キャッシュ、抽出器更新、API停止、途中再開を再現する。
- 材料不足の試合へ転機・因果・段落数を強制する。

公開前ゲートは失敗注入の重大な誤りをすべて拒否しなければならない。`recap-articles.json` に候補が残っていても、編集品質の未評価状態では自動的に「高品質」「完成」と表示しない。

## 6. 実装順序の改訂

1. 旧解析の時刻付きデータ率と失敗理由を出し、`analysisVersion` の変更で旧キャッシュが確実に再解析される経路を作る。
2. 6対戦のゴールド評価セットを用意し、1/2/4/5 FPS、Agentic、音声経路を比較する。APIキーがないローカルでは合成・保存データ評価を行い、実映像評価を行ったように扱わない。
3. 根拠カードの形式と独立再確認を固め、正しい時刻と内容の採点を行う。
4. 文ごとの根拠意味対応、事実の断定と発言帰属、公式矛盾を試験し、反例を落とす品質ゲートを実装する。
5. S/Fの編集原稿を事実入力に使わず、文体見本として使う記事執筆A/Bを行う。人手盲検評価に合格したモデル・プロンプトだけを採用する。
6. 2節分のshadow運用を行う。合格率、レビュー修正率、見落とし、費用が実測基準内なら、試合ごとの限定自動公開へ進む。

## 9. 再設計に基づく実装状況

- 旧動画解析キャッシュは `analysisVersion`、モデル一覧、FPS、動画ID、区間のいずれかが変われば再解析対象とし、旧runsは `staleRuns` に保存する。
- 動画解析プロンプトで時刻をクリップ先頭基準と明示し、保存前にアーカイブ全体の時刻へ変換する。両端時刻がない話題は再確認可能な根拠にしない。
- 根拠候補の再確認では主張を先に提示せず、モデルにクリップを独立に説明させる。説明と候補の一致が弱いものは `disputed` にする。
- 各記事文と参照根拠の語句重なりを追加確認し、無関係な文章を有効なIDで通す反例を拒否する。これは機械的な保守フィルターであり、意味理解や編集品質の証明ではない。
- 自動生成記事は既定でshadow候補として保存し、公開記事にしない。`RECAP_PUBLICATION_MODE=auto` は評価基準を満たしてから明示設定する。候補はUIで確認待ち、公式結果は速報として維持する。
- 15分間隔のGitHub Actions workerで、解析・執筆状態を再開可能にした。実運用のSecrets/VariablesとActions実行はPRマージ後の確認が必要。
- 次の受入れ前に、S/Fの最低6対戦を2名でラベル付けし、方式別に時刻精度・重要事実の再現率・重大誤り・記事の盲検品質・費用を比較する。API疎通だけで自動公開へ切り替えない。
