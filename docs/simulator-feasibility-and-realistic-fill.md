# 残り試合シミュレーター：到達可能性の厳密判定と、統計にもとづく自動埋め

2026-11-09 時点の設計。実装前に方針を合意するための文書。

## 1. 背景と目的

シーズン終盤になり、ポイント差から「もう届かない順位」が出てきた。しかし今の表示はモンテカルロ（1万回）の確率だけなので、次の2つを区別できない。

- **数学的に不可能**：どんな結果になっても届かない。
- **可能だが、1万回の試行では一度も起きなかった**：とても起きにくいが、ゼロではない。

2026-11-09 の結果で、全通りを数え上げる試作（§3）を回すと、実際に次のようなずれがあった。

| チーム | 目標 | モンテカルロ | 厳密な判定 | 今の表示 |
|---|---|---|---|---|
| 広島 TEAM iXA（S） | 1位 | 0% | **不可能** | 「絶望的（ほぼ不可能）」 |
| 広島 TEAM iXA（S） | 3位以内（プレイオフ） | 0% | **可能** | 「絶望的（ほぼ不可能）」 |
| 名古屋NTPOJA（F） | 1位 | 0% | **可能** | 0% |

もう一つの課題は「自動埋め」である。今の `generateOutcomesForTargetRank` は、勝ち負けを乱数で決め、目標の順位に届くまで探す。結果は「起こりうる」が「起こりやすい」とは限らず、その根拠も画面に出ていない。

**目的**

1. 0.1% でも可能性があれば確率を出し、数学的に不可能なら「不可能」とはっきり出す。届くことが決まった場合は「確定」と出す。
2. 自動埋めは、これまでの結果から学習した予測モデルの確率で「最も起こりやすい展開」を選ぶ。
3. その根拠（モデル、データの更新日、各試合の予測、選ばれた展開の起こりやすさ）をページ上部に出す。

## 2. 前提（順位の決まり方とデータ）

- 順位は ①獲得ポイント → ②バトル得失差 → ③ラウンド得失差 の順で決まる（`sortStandings`）。上位3チームがプレイオフ、1位は決勝シード。
- 1試合のポイントは 6 通り：40-0 / 30-10 / 30-20（延長） / 20-30 / 10-30 / 0-40。
- シミュレーターは得失差を代表値で扱う（例：40-0 は常にバトル +5・ラウンド +8）。しかし実際の値は幅が大きい。2026 年の実績では、40-0 のバトル差は +3〜+6、10-30 でも 0〜-4 だった。
  - そのため「ポイントは同点、得失差で決まる」状況を、代表値だけで「可能／不可能」と決めてはいけない。
- 未消化の試合数（11/9 時点）：S は 9 試合、F は 12 試合。

## 3. 到達可能性の厳密判定

### 3.1 判定の内容

各チームについて、次の4つを決める。

| 判定 | 意味 |
|---|---|
| 最良の順位 `bestRank` | 自チームに最も都合のよい結果がそろったときの順位 |
| 最悪の順位 `worstRank` | 最も都合の悪い結果がそろったときの順位 |
| 得失差次第 `tiebreakDependent` | 上の順位が、ポイント同点で得失差に左右されるか |
| 最良のケース `bestCaseScenario` | 最良の順位になる結果の一例（試合 ID → スコア） |

ここから、目標ごとの状態を次のように決める。

- 1位：`bestRank = 1` なら可能、`worstRank = 1` なら確定。
- プレイオフ：`bestRank ≤ 3` なら可能、`worstRank ≤ 3` なら確定。

### 3.2 計算方法

1. **最良の順位を求めるとき**は、自チームの残り試合をすべて 40-0 の勝ちにする。40-0 は自チームのポイントと得失差を最大にし、相手のポイントを最小にするので、どの順位を目指す場合でもこれより悪くなることはない。
2. 残りの他チームどうしの試合を、6 通りすべて深さ優先で数え上げる。各組み合わせで、自チームより確実に上のチーム数と、同点のチーム数を数える。
3. 枝刈りをする。途中で「確実に上にいるチーム」が目標の順位を超えたら、その枝は打ち切る。各チームの残りの最大・最小ポイントを先に計算しておき、ポイント上の上限・下限で判断する。
4. **最悪の順位を求めるとき**は、自チームの残り試合をすべて 0-40 の負けにして、同じように数え上げる。
5. **ポイントが同点のとき**の扱いは次のとおり。
   - スコアごとにバトル・ラウンド得失差がとりうる幅を、試合形式から求める。先鋒・中堅・延長は2本先取、大将は3本先取。この幅は、これまでの全試合が幅の中に収まることをテストで確かめる。
   - 「自チームの得失差の最大」が「相手の得失差の最小」を下回る場合だけ「確実に下」とする。幅が重なる場合は「得失差次第」とする。
   - こうすることで、「不可能」と出すのは本当に不可能なときだけになる。判定が甘くなるのは「得失差次第」の側だけで、その場合はそのとおりに表示する。

### 3.3 計算量

試作では、S と F の全12チームについて最良・最悪の両方を数え上げて、約3.7秒だった（枝刈りなし、Node）。

- 自チームの試合を固定すると、残りは S が最大 6 試合、F が最大 8 試合（6⁸ ≒ 168万通り）。枝刈りを入れれば、さらに一桁以上減る見込み。
- ブラウザでも、ユーザーが入力した試合を固定してから数え上げる。入力が進むほど速くなる。画面が止まらないように Web Worker で回す。
- シーズン序盤のように残り試合が多いとき（1ディビジョン 15 試合超など）は、上限時間（例：2秒）で打ち切る。その場合は「判定中（概算）」とし、モンテカルロの結果だけを出す。

### 3.4 表示

確率の表示と状態を、次のように組み合わせる。

| 状態 | 表示 | 条件 |
|---|---|---|
| 確定 | 「確定」 | `worstRank` が目標以内で、得失差に左右されない |
| 確率あり | 「18.5%」 | 可能で、モンテカルロの確率が 0.1% 以上 |
| ごくわずか | 「0.1%未満（可能性あり）」 | 可能だが、モンテカルロでは 0.1% 未満 |
| 得失差次第 | 「得失差次第で可能」 | ポイントは同点まで届くが、上回れない |
| 不可能 | 「不可能」 | `bestRank` が目標より下 |

- 「不可能」と「得失差次第」には、理由を1行添える。例（iXA の1位）：「全勝しても最大190pt。ZETA（現在190pt）は残りで1点でも取れば190ptを超え、全敗すると対戦相手の SOL と FAV が190ptを超える」。
  - 理由は、最良のケースで iXA より上に残るチームと、その原因になる試合から組み立てる。
- 「最良のケースを入力」ボタンを置き、`bestCaseScenario` をそのまま表に入れて確かめられるようにする。
- 既存の `evaluateRankFeasibility` は、確率 0.3% 未満を一律に「絶望的（ほぼ不可能）」としている。これをやめ、厳密判定で不可能なときだけ「不可能」とする。可能なら確率が低くても「奇跡的・要他力」とする。
- チームページの見通し（`personalizedOutlook`・`routes`）も同じ判定を使う。不可能な目標のルートは「数学的に消滅」として出す。

## 4. 統計にもとづく自動埋め

### 4.1 使う確率

予測モデル v2（`model-v2.json`）が、未消化の試合ごとに 6 通りのスコアの確率（`outcomeWeights`）を出している。今のモンテカルロはこれを使っているが、`scenarios.json` には勝率と最有力スコアしか保存しておらず、画面では使えない。

- パイプラインで、未消化の全試合について `matchPredictions[matchId] = { weights, homeWinProbability, mostLikely }` を `scenarios.json` に保存する。
- ブラウザでは、この表を読むだけにする。モデル本体（`player-stats.json` は約 400KB）は送らない。

### 4.2 埋め方

| ボタン | 動き |
|---|---|
| 「最も起こりやすい展開で埋める」（新設） | 各試合で確率が最大のスコアを選ぶ。試合は互いに独立なので、全体でも最も起こりやすい展開になる |
| 「推しチーム×目標順位で埋める」（作り直し） | 目標の順位になる展開のうち、確率の積が最大のものを選ぶ |
| 同じボタンをもう一度押す | 2番目、3番目に起こりやすい展開を順に出す（上位5件まで） |

目標順位つきの探索は、次のように行う。

- 各試合の対数確率の和を最大にする分枝限定法を使う。上限は「ここまでの和 ＋ 残りの試合の最大対数確率の和」とする。
- 順位の判定は、表示と同じ `calculateStandings`（代表値の得失差）で行う。
- 上位5件は、優先度つきキューで良い順に取り出す。
- 目標が不可能な場合（§3）は探索しない。ボタンを押せないようにし、「不可能」と理由を出す。
- 「得失差次第」でしか届かず、代表値では再現できない場合は、「実際の得失差しだいで可能。代表スコアでは再現できません」と出す。

### 4.3 今の乱数版の扱い

今の `generateOutcomesForTargetRank` は、新しい探索に置き換える。URL の `?team=…&rank=…` から開いた場合も同じ探索を使い、乱数をなくす。そうすると、同じ URL からはいつも同じ展開が出る。

## 5. 根拠の表示（ページ上部）

シミュレーターのページ上部に、たたんで開ける「この予測の根拠」パネルを置く。

1. **データ**
   - 何節まで反映しているか、更新日時。
   - モンテカルロの回数（1万回）。
2. **モデル**
   - 予測モデル v2 の要点：選手の実力値、キャラ相性、HOME の後出し有利。SFL の全履歴と start.gg の大会成績で学習している。
   - オーダーは発表前なので、過去の起用傾向からの分布を使っていること。
   - 実力値の不確かさとして 200 通りの世界をサンプルしていること。
   - 2026 年レギュラーシーズン 68 ボウトでの成績（対数損失 0.646、Brier 0.229。常に 50% と予想した場合は 0.693 と 0.250）。`docs/model-eval-report.md` から自動で出す。
3. **自動埋めした展開の根拠**
   - その展開の確率と、起こりやすさの順位（例：「目標を満たす展開の中で1番目」）。
   - 予想が外れた（モデルの最有力ではない結果を選んだ）試合の数と、その試合のモデル上の確率。例：「ZETA vs FAV で FAV の 30-10 勝ち（確率 21%）」。
4. **判定の意味**：「不可能」「得失差次第」「確定」の定義を1行ずつ。

あわせて、各試合のカードに「HOME 勝率 58% ／ 最有力 30-10」を小さく出し、どの結果を選んだかを見比べられるようにする。

## 6. 実装の単位

| # | 内容 | 主なファイル |
|---|---|---|
| 1 | スコアごとの得失差の幅を、試合形式から求める。実績が幅に収まることをテストする | `src/lib/score-format.ts`（新規） |
| 2 | 厳密判定（数え上げ、枝刈り、得失差の幅、最良ケース） | `src/lib/feasibility.ts`（新規） |
| 3 | パイプラインで、判定と各試合の確率表を `scenarios.json` に保存。スキーマを更新 | `scripts/` のシナリオ生成、`src/lib/schema.ts` |
| 4 | 見通しの文言を判定に合わせる | `src/lib/simulator.ts`（`evaluateRankFeasibility`、`buildPersonalizedOutlook`） |
| 5 | 最も起こりやすい展開の探索（目標順位つき、上位5件） | `src/lib/simulation-code.ts`（置き換え） |
| 6 | シミュレーターの画面：状態の表示、Web Worker での再判定、ボタン、根拠パネル | `src/components/InteractiveSimulator.tsx`、`src/pages/simulator.astro` |
| 7 | ダッシュボードとチームページの表示を同じ状態に合わせる | `src/components/DivisionDashboard.tsx`、`src/pages/team/` |

1〜4 で表示の正しさ、5〜6 で自動埋めと根拠、7 で全体の統一ができる。PR は 1〜4、5〜6、7 の3本に分けるのがよい。

## 7. テスト

- **厳密判定**
  - 小さな架空のリーグで総当たりと突き合わせ、bestRank・worstRank が一致すること。
  - 11/9 時点の固定データで、iXA の1位が不可能、3位以内が可能、NTPOJA の1位が可能になること。
- **得失差の幅**：2026 年の全実績（39 試合）が、それぞれのスコアの幅に収まること。
- **自動埋め**
  - 小さな例で総当たりと比べ、目標を満たす展開の中で確率が最大のものを返すこと。
  - 2回目以降は、確率が下がる順に別の展開を返すこと。
  - 不可能な目標では展開を返さず、理由を返すこと。
- **表示**：状態の対応表（§3.4）どおりの文言になること。
- 既存の `generateOutcomesForTargetRank` のテストは、「可能な目標なら必ず届く」「不可能な目標なら返さない」に書き換える。

## 8. 決めておきたいこと

1. **プレイオフの枠**：上位3チームでよいか。1位が決勝シード、2位が準決勝 HOME という扱いも今の実装どおりでよいか。
2. **「0.1%未満」の出し方**：モンテカルロで 0 回だった場合は「0.1%未満（可能性あり）」だけを出す案にしている。数え上げで正確な確率まで出す方法もあるが、S で約1,000万通り、F で約22億通りになるので、今回は見送る案にしている。
3. **自動埋めの「もう一度押す」**：上位5件を順に出す案にしている。モデルの確率に従ってランダムに引く方式もありうる。
